# EQE · Sincronización y versión v98

## Problema y comportamiento

La PWA enviaba el snapshot completo y, ante un 409 del servidor, conservaba la copia local pero quedaba detenida en «Copias distintas». El encabezado mostraba v80 fija, mientras APP_VERSION era 82, exportación 83 y recursos CSS/JS 97. main no acredita el código realmente publicado en cada dispositivo.

La candidata compara por dispositivo una base persistida con el estado local y el remoto. Combina cambios independientes de canciones y pases, reintenta ante revisiones concurrentes y agrupa letra/acordes de cada canción para no mezclar índices incompatibles. Una modificación simultánea de la misma canción conserva las dos variantes y pide elegir, con descarga de ambas. La primera actualización sin base compartida no presume cuál era correcta.

## Cambios

- sync-merge.js: motor puro, compatible con navegador y Node, sin dependencias externas.
- sync-client.js: red, persistencia, recuperación con journal, estado de sincronización y revisión de conflictos. Reutiliza /api/sync y la revisión CAS del Worker existente. No modifica esquema ni datos D1. El Worker añade únicamente un bloqueo de API para las vistas previas de esta aplicación antes de cualquier acceso a D1.
- Reintento en apertura, foco, vuelta de conexión y cada 15 segundos con app visible. Se aplaza mientras el editor está abierto. No puede sincronizar sin red ni garantizar ejecución de fondo cuando iOS suspende la PWA.
- Los cambios realizados durante una petición no se marcan como enviados; se conservan para la siguiente ronda.
- La versión cargada se muestra desde APP_VERSION y se exporta como buildVersion. APP_VERSION, version.json, caché y referencias de los módulos nuevos usan v98. El campo version:79 del exportador conserva la versión del formato, no la versión de la app.
- Reparación de la cadena HTML de impresión ya identificada en PR51; se conserva fuera de la cadena el ayudante existente de portapapeles. El resto de PR49 no se incorpora.
- Los pases abiertos se actualizan después de recibir datos. Las cachés ajenas no se borran y no se almacenan respuestas HTTP fallidas.

## Datos y auditoría

Los datos privados y candidatos de recuperación se conservan fuera de GitHub. La copia combinada mantiene las 95 canciones del iPad, incorpora la canción adicional de la nube y conserva las variantes de ambos orígenes en archivos separados. No ha sido importada. No se escribe en producción durante esta intervención.

La auditoría comparativa disponible no certifica una letra original aprobada ni sustituye exportaciones actuales del Mac/iPhone. Donde la nube no almacena letra explícita, se requiere verificar el recurso base realmente instalado. No se corrigen letras con fuentes de Internet ni se elige automáticamente una armonía.

## Antes de publicar

1. CI verde, incluido Chromium/WebKit, y validar importación del candidato en almacenamiento aislado.
2. Contrastar assets/Worker realmente desplegados con main: la versión estable está POR VERIFICAR según .gitop/PROJECT_STATE.md; una publicación completa de main podría revertir mejoras manuales posteriores.
3. Exportar Mac e iPhone y confirmar referencia original para completar auditoría y revisión de conflictos históricos.
4. Validar en los tres equipos físicos: una canción diferente en cada uno, recuperación offline, conflicto de una misma canción, pases y conservación de letra/acordes.
5. Publicación únicamente con autorización; el merge a main activa el workflow de producción existente. No fusionar como forma de probar.

## Reversión

Antes del despliegue conservar la versión real de assets/Worker y exportaciones de los tres dispositivos, más snapshot de nube. No restaurar datos completos para revertir solamente código. Los metadatos qeSync.* son locales; no borrar almacenamiento para actualizar. Una vuelta al cliente antiguo no ofrece las garantías nuevas de combinación.
